## 1. Intent

The BDD CI gate on `develop` is broken on `apps/api#build` in a clean Linux environment. `apps/api/tsconfig.json` compiles BOTH `apps/api/src/**/*.ts` AND `../libs/features/{auth,transactions}/shared/schemas/**/*.ts` (lines 35–39); 15 of those files `import { z } from "zod"`. With `moduleResolution: "node"` (Node10, tsconfig.json:5), TypeScript walks ancestors looking for `node_modules/zod` from each compiled file's location. **The schema files live in orphan directories** — `libs/features/{auth,transactions}/shared/` has no `package.json` and no `node_modules/`, so the walk never finds a zod symlink, and TS2307 fires. The verify report's "pnpm hoisting differs" hypothesis (Engram #2316) was INCOMPLETE: the real root cause is the orphan-directory layout, not pnpm's hoist strategy. The reproducer (with HOME pollution `~/node_modules/zod` temporarily moved aside) produces all 15 errors verbatim (5 in `apps/api/src/`, 10 in the orphan schemas). Locally the bug is masked because TypeScript walks past the project root and finds zod in the user's HOME directory; CI's GitHub Actions runner has no such pollution, so it fails every time. PR #63 (`fix-bdd-tsx-node22`) was admin-merged with the BDD gate bypassed because this latent issue was unfixed — fixing it closes the BDD gate permanently. Fix shape is A' (compound): move `zod` from `devDependencies` to `dependencies` in `apps/api/package.json` (closes the 5 `apps/api/src/` errors) AND add a `paths` mapping for `zod` in `apps/api/tsconfig.json` (closes the 10 orphan-schema errors). Same change, two angles: `dependencies` for runtime + the immediate `apps/api/src/` walk; `paths` for compile-time orphan-schema resolution.

## 3. Approach

Two coordinated config edits. No code, no tests, no schema changes, no infra changes.

### 3.1 Step 1 — `apps/api/package.json`: move zod to `dependencies`

```diff
   "dependencies": {
     "@auth/prisma-adapter": "2.7.4",
     ...
     "rxjs": "7.8.1",
+    "zod": "^4.4.3"
   },
   "devDependencies": {
     "@nestjs/cli": "11.0.23",
     ...
     "vitest": "4.1.9",
-    "zod": "^4.4.3"
   }
```

**Why this works**: pnpm MUST link `apps/api/node_modules/zod -> .pnpm/zod@4.4.3/node_modules/zod` once zod is declared as a runtime dep. From `apps/api/src/**/*.ts` files, TypeScript's Node10 walk finds zod in the immediate `apps/api/node_modules/zod` and resolves cleanly. This closes the **5** TS2307 errors in `apps/api/src/` (`auth.controller.ts:78`, `:81`; `body.decorator.ts:2`; `query.decorator.ts:2`; `zod-validation.pipe.ts:3`).

**What this does NOT fix**: the 10 orphan schema files in `libs/features/{auth,transactions}/shared/schemas/`. From those files, the ancestor walk still doesn't reach `apps/api/node_modules/zod` (different subtree). Step 2 closes that.

### 3.2 Step 2 — `apps/api/tsconfig.json`: add `paths` mapping for `zod`

```diffc
+    // zod path mapping closes the orphan-schema resolution gap:
+    // `libs/features/{auth,transactions}/shared/` has no package.json, so
+    // Node10 ancestor-walk cannot reach zod. This mapping intercepts ALL
+    // files compiled by apps/api's tsc (including the orphan schemas).
     "paths": {
       "@core/database": ["libs/core/database/src"],
       ...
       "@shared-utils/*": ["../libs/shared-utils/*"],
+      "zod": ["../../node_modules/.pnpm/zod@4.4.3/node_modules/zod"]
     }
```

**Why this works**: TypeScript's `paths` mapping intercepts the bare specifier `zod` BEFORE the Node10 ancestor walk. The mapping points to pnpm's canonical storage location (`node_modules/.pnpm/zod@<version>/node_modules/zod`), which is the same path pnpm itself uses for symlink targets — it is stable across pnpm versions and immune to package-level hoisting strategy changes. The mapping is a **TypeScript-only construct**: at compile time the schema files resolve zod via the mapped path; at runtime, Node follows the `import` to wherever zod is actually installed (now `apps/api/node_modules/zod` after Step 1, plus the existing `libs/features/*/server/node_modules/zod` symlinks for slice-runtime code).

**Why pnpm-canonical path, not workspace-hoisted**: the path `../../node_modules/zod` (workspace root) would also work in many setups, but it depends on pnpm's hoist pattern. The pnpm-canonical path (`../../node_modules/.pnpm/zod@4.4.3/node_modules/zod`) is guaranteed by pnpm's storage layout — it is where every `node_modules/zod` symlink ultimately points — and is invariant across `public-hoist-pattern` settings.

### 3.3 Step 3 — Regenerate the lockfile

```bash
pnpm install --frozen-lockfile   # EXPECTED to fail the first time (lockfile stale)
pnpm install                     # regenerates pnpm-lock.yaml (zod moves devDep → dep)
git diff pnpm-lock.yaml          # INSPECT — only the apps/api snapshot table for zod should change
```

**Why this happens**: pnpm records which packages list zod as a dep vs devDep in the lockfile's `snapshots` table. Moving zod from devDep to dep causes pnpm to relocate the zod entry between sections. The diff is cosmetic (snapshot re-ordering) and deterministic.

### 3.4 What the fix changes (concretely)

```diffc
// apps/api/package.json (1 line moved from devDependencies to dependencies)
-  "zod": "^4.4.3"   // ← devDeps end
+  "zod": "^4.4.3"   // ← deps end

// apps/api/tsconfig.json (1 entry added to compilerOptions.paths, +3 JSDoc lines)
+    // zod path mapping closes the orphan-schema resolution gap:
+    // `libs/features/{auth,transactions}/shared/` has no package.json, so
+    // Node10 ancestor-walk cannot reach zod. This mapping intercepts ALL
+    // files compiled by apps/api's tsc (including the orphan schemas).
+    "zod": ["../../node_modules/.pnpm/zod@4.4.3/node_modules/zod"]

// pnpm-lock.yaml — auto-regenerated, snapshot table reorder
```

### 3.5 Why not Shape B (`public-hoist-pattern` in `pnpm-workspace.yaml`)

Setting `public-hoist-pattern: ["*zod*"]` (or even just `["zod"]`) would hoist zod to the workspace root `node_modules/zod`, fixing the orphan walk by making zod reachable from any subtree. Rejected for v1 because:

- **Workspace-wide blast radius**: every package gains an implicit zod dep, weakening the explicit-deps invariant. Future packages might import zod via the root symlink without declaring it.
- **Dual-version conflict**: `apps/web` pins `zod@3.24.1`, `apps/api` uses `zod@4.4.3`. A naive `public-hoist-pattern: ["*zod*"]` would create a conflict at the root — pnpm would refuse to install, OR would shadow one version with the other, breaking either apps/api or apps/web. Surgical fix patterns (`["zod@4"]` or `["zod@3"]`) exist but require version-string matching in a workspace config — fragile and surprising.
- **Conceptual mismatch**: the schema files use zod because each slice's `server/` package owns them at runtime; the orphan-directory layout is the real architectural smell. `public-hoist-pattern` papers over it differently than the targeted `paths` mapping.

### 3.6 Why not Shape C (devDep → dep only — parent's original hypothesis)

This is what Engram #2316 / the parent's prompt originally proposed. Empirically verified (explore brief §1, §3) to be **INSUFFICIENT**: it closes the 5 `apps/api/src/` errors but leaves all 10 orphan-schema files broken in CI. A "looks fixed, isn't" PR would be worse than the current state because the failure would be invisible until the next orphan-schema edit. Shape A' (compound, this proposal) is mandatory.

## 8. Rollback Plan

**Whole-change**: `git revert <merge-sha>` on `develop` undoes the single PR cleanly. The two source edits revert to the pre-fix state (`zod` returns to `devDependencies`; the `paths` mapping is removed); the lockfile reverts to its pre-fix content-hash. `apps/api#build` fails on the same 15 TS2307 errors it fails on today. Acceptable because the BDD gate was already broken on `develop` (the pre-fix state) — reverting only restores the known-bad baseline. The next opportunity for a follow-up fix would be a fresh PR (the duplicate-dep cleanup + orphan-directory fix could be combined).

**Per-file rollback** (independent revert of either change):
- Revert `apps/api/package.json` only: zod returns to `devDependencies`. The 5 `apps/api/src/` errors return; the 10 orphan-schema errors remain closed (the `paths` mapping still resolves them). Acceptable as a half-fix — the BDD gate still passes via the `paths` mapping alone, but `apps/api` loses its runtime zod declaration (debatable, since zod types are erased at runtime).
- Revert `apps/api/tsconfig.json` only: the `paths` mapping is removed. The 5 `apps/api/src/` errors stay closed (devDep move still works); the 10 orphan-schema errors return. **NOT acceptable as a half-fix** — the BDD gate fails because the orphan schemas are compiled by `apps/api`'s tsc.

**Will NOT do**: force-push, rewrite history, touch `main`, modify `openspec/changes/{fix-bdd-tsx-node22,vertical-slicing-reference-scaffold,fix-api-nestjs-di}/`, amend any prior commit, change Node version, change pnpm version, swap to Shape B/C inline (those are separate changes), add a `package.json` to `libs/features/*/shared/` (separate change, deferred to follow-up).
